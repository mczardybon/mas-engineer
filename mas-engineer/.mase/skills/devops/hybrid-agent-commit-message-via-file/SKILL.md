# Long Commit Messages in Hybrid Agent Sessions (2026-07-28)

## The Problem

You're in a Hermes-style hybrid agent (Python `execute_code` +
file-based `write_file` + `patch` tools). You need to make a
`git commit` with a multi-line, structured message (wrench R-format
from mas-engineer-commit-protocol, or any convention with 5+
sections).

**Naive approach (FAILS):**

```python
import subprocess
msg = "wrench R-N -- title\n\nBug: ...\nFix: ...\n"
subprocess.run(['git', 'commit', '-m', msg])
```

Result: `fatal: could not get a message` OR the message gets split
on whitespace, with all newlines collapsed into single spaces.

**Why:** When `subprocess.run` is given a list and `shell=False` (the
default), git's `-m` flag receives the entire string as ONE arg, but
`os.execvp` splits on internal whitespace at the OS level. Embedded
newlines (`\n`) and backticks also break arg parsing.

**Wrong fix #1:** `shell=True` + escaped quotes — works for short
strings, breaks on messages with embedded `$`, backticks, or
unbalanced quotes.

**Wrong fix #2:** Multiple `-m` flags:
```python
subprocess.run(['git', 'commit', '-m', 'title', '-m', 'body'])
```
This creates a `title\n\nbody` commit (with \n\n between), but you
lose all internal newlines in the body. The whole point of a
structured commit message is lost.

## The Correct Pattern (always use this)

```python
# Step 1: write the message to a file with write_file (NOT echo/heredoc)
# write_file /tmp/commit-msg.txt is a tool call, returns bytes_written

# Step 2: commit with -F file
subprocess.run('git commit -F /tmp/commit-msg.txt', shell=True, capture_output=True, text=True)
```

**That's it.** Two steps, both robust, both work with messages of
any length or content.

## Variations

### Variation A: message generated by Python (no write_file available)
```python
# Even if you only have terminal, use a temp file, not -m:
import tempfile, subprocess
with tempfile.NamedTemporaryFile(mode='w', suffix='.txt', delete=False) as f:
    f.write(msg)
    tmppath = f.name
subprocess.run(f'git commit -F {tmppath}', shell=True)
os.unlink(tmppath)
```

### Variation B: file is a one-shot tool call (write_file)
```python
# write_file is a single tool call, no need to cleanup:
write_file('/tmp/commit-msg.txt', content=msg)  # tool call
subprocess.run('git commit -F /tmp/commit-msg.txt', shell=True)
```

### Variation C: message contains `$` or backticks (no escape problems)
Same as A or B. The whole point of `-F` is that the shell doesn't
interpret the file contents.

### Variation D: pre-commit hook needs to scan
The hook runs `git diff --cached`, which doesn't see the message.
So the message content is irrelevant to the hook — only the diff matters.
Don't worry about hooks when crafting the message; the diff is what
they see.

## When `-m` is OK (only these cases)

- Single-line short message (subject only, no body)
- Message has no backticks, no `$`, no unbalanced quotes
- You're using `shell=True` and are sure about the quoting
- The message will fit in your head if the newlines are collapsed
  to spaces (i.e. no structural sections)

If ANY of these is false: use `-F` file.

## Related gotchas

**Gotcha 1: working directory doesn't persist across execute_code calls.**
Each call to `execute_code` is a fresh Python process. `os.chdir()`
in one call does NOT carry over. Solutions:
- Use absolute paths: `subprocess.run('git -C /abs/path/log status', shell=True)`
- Pass `cwd=`: `subprocess.run('git status', shell=True, cwd='/abs/path')`

**Gotcha 2: env vars don't persist either.**
`os.environ['X'] = 'Y'` in one call doesn't carry over. Solutions:
- Pass `env=` explicitly: `subprocess.run(..., env={'X': 'Y', **os.environ})`
- For PATs: re-read from `.env` file at the start of each call.
- For this reason: store PATs on disk, NOT just in-memory.

**Gotcha 3: shell=True + interactive commands hang.**
For `git commit` it's fine. For anything that reads stdin
(`git rebase -i`, `git add -p`), use `pty=True` or the
background process tool. Don't try to script it via subprocess.

**Gotcha 4: write_file echoes content back.**
If your file content contains a secret, the `write_file` tool
return value (`bytes_written` + path) doesn't echo, but the
content is in YOUR context window. If you then `subprocess.run`
and print the output, the secret might leak via the printed
output. Redact secrets BEFORE writing, not after.

## Pre-Commit Checklist (Hybrid Agent, Long Message)

Before `git commit -F /tmp/msg.txt`:
1. `msg.txt` exists and has > 1 line (if single line, just use `-m`)
2. `msg.txt` has no embedded `***REDACTED***` (only if you actually
   redacted; placeholder is fine)
3. The diff is staged: `git diff --cached --stat` shows what you expect
4. Pre-commit hook scanned the diff (not the message) — manually
   if hooks aren't installed
5. Commit author is configured correctly

After commit:
6. `git log --oneline -1` shows the new commit
7. `git show HEAD --stat` shows the correct file list (NOT just the message)
8. The full message: `git log -1 --format=%B HEAD`
