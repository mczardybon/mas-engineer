## Bug

R110-316 added the 3-source lockstep test that catches `recipe/sub/*.yaml`
0-byte files at pre-push time. But R110-316 does NOT catch the
`tests/test_zz_*.py` zombie class: ephemeral test-side-effect files
created by `test_r110279_runtime_var_skip.py` (and any future tests
using the same pattern).

Pattern: a test creates an ephemeral `tests/test_zz_*.py` file as
part of its test logic, with cleanup in a `try/finally: os.unlink()`
block. If `pytest-timeout` kills the test mid-run, the `finally`
block is SKIPPED, and the file persists as a zombie.

R110-295 documented this exact issue: a leftover `test_zz_r110279_*.py`
file had to be manually `rm`-ed before pre-push:

```text
# pre-R110-318: zombie stays on timeout kill
$ timeout 30 python3 -m pytest tests/test_r110279_runtime_var_skip.py
Killed (pytest-timeout)
$ ls tests/test_zz_*.py
tests/test_zz_r110279_*.py  # zombie still there
# developer has to:
$ rm tests/test_zz_*.py
```

The R110-316 3-source lockstep test catches `recipe/sub/*.yaml`
zombies at pre-push, but `tests/test_zz_*.py` was not in its scope.

## Root cause

The R110-279 pattern (ephemeral test files with `try/finally: cleanup`)
has no source-level enforcement that the cleanup actually runs. The
`finally` block is best-effort and skips on:
  - pytest-timeout SIGKILL
  - OOM kill
  - Ctrl-C / developer abort
  - any other signal that bypasses normal Python exception handling

The drift class is "incomplete cleanup" — a runtime/environment
issue, not a code-logic issue. R110-318 closes this gap with a
session-start auto-cleanup that runs BEFORE pytest collection, so
the developer always starts from a clean state.

## Fix

1. **Add `pytest_sessionstart` hook in `mas-engineer/tests/conftest.py`**
   that runs before pytest collection and:
   - auto-DELETES `tests/test_zz_*.py` (and matching `.pyc`)
   - emits WARNING (read-only) for `recipe/sub/*.yaml` 0-byte files
     NOT in the `RECIPE_EXCLUDE` allowlist
2. **Add 7 tests** in
   `mas-engineer/tests/test_r110318_session_start_zombie_cleanup.py`:
   - `test_clean_zombie_test_zz_file` — single zombie removed
   - `test_clean_zombie_pycache` — matching `.pyc` also cleaned
   - `test_legitimate_test_files_untouched` — `tests/__init__.py`
     (0-byte by convention) NOT touched
   - `test_warn_on_unhandled_recipe_sub_yaml` — WARNING + file kept
   - `test_no_warning_when_recipe_sub_yaml_in_allowlist` — no warn
     when in allowlist
   - `test_no_op_when_no_zombies` — clean state produces no output
   - `test_multiple_zombies_all_cleaned` — 5 zombies all cleaned

The hook is read-mostly by design: only `tests/test_zz_*.py` is
auto-deleted. `recipe/sub/*.yaml` is WARNING-only because a 0-byte
file might be a legitimate fixture (deletion would be too dangerous).
R110-316 will FAIL on pre-push if the WARNING is not addressed,
giving two layers of protection.

## E2E (real pytest run, dual-direction verification)

The 7 new tests cover both directions of behavior:

```text
# Direction 1: zombie-exists → cleanup
$ touch mas-engineer/tests/test_zz_r110318_zombie.py
$ cd mas-engineer && python3 -m pytest tests/test_r110318_session_start_zombie_cleanup.py::test_clean_zombie_test_zz_file -v
PASSED
$ ls mas-engineer/tests/test_zz_r110318_zombie.py
ls: cannot access ...: No such file or directory   # cleaned

# Direction 2: zombie-allowed-in-allowlist → no warning
$ touch mas-engineer/recipe/sub/sub_-.yaml
$ python3 -m pytest tests/test_r110318_session_start_zombie_cleanup.py::test_no_warning_when_recipe_sub_yaml_in_allowlist -v
PASSED
$ ls -la mas-engineer/recipe/sub/sub_-.yaml
-rw-r--r-- 1 user user 0 ...   # still there (read-mostly)

# Real conftest run (no fakes, no monkeypatch)
$ touch mas-engineer/tests/test_zz_real_zombie.py
$ python3 -m pytest tests/test_pre_push_check_1_5_skill_alignment.py -q
$ ls mas-engineer/tests/test_zz_real_zombie.py
ls: cannot access ...: No such file or directory   # cleanup works on real conftest too
```
