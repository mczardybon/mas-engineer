## Bug

R110-296 (913d6f7) introduced a regression that was discovered
during the full-suite regression sweep:

- `mas-engineer/STATUS.md` R110-296 section
- `mas-engineer/docs/CHANGELOG-2026-08-29-r110-296.md`
- `logs/e2e-evidence-gen2/R110-296-FIX-SD-TEST-DRIFT.md`

All 3 docs contained the new R110-279 synth-literal value
`<REDACTED-R110296-synth-literal>` (and its sub-parts
`<REDACTED-subpart>`, `<REDACTED-subpart>`)
in narrative sections, code-block examples, and shell
command examples. This violated the **R110-78
body-claim-drift protocol**: the synth-literal is INTENDED
to appear in EXACTLY 1 source file at scan-time (the test
source), so that the detector's `_is_common_value()` function
flags the synth-test file with 1 finding. By referencing the
literal in 3 additional docs, the literal appeared in
**4 total files** → `_is_common_value` short-circuited on
2+ matches → detector returned 0 findings → synth test
FAILED.

**Symptom:**


This is the **EXACT same R110-78 verification-theater pattern**
that R110-279 (289780e) and R110-296 (913d6f7) were trying to
prevent. I caused a regression in my own regression-fix.

## Root cause

When I wrote R110-296's narrative, I inlined the synth-literal
value in CHANGELOG, STATUS, and EVIDENCE files to "make the
fix clear and traceable". This was a direct violation of the
R110-78 protocol: any string that the SD-test detector
searches for in source code (as a potential stale-literal
finding) must NOT appear in multiple source locations, OR
the `_is_common_value` skip-rule will suppress the finding.

The R110-279 fix relied on the literal being unique to the
synth-file. My docs broke that uniqueness.

## Fix

- Replaced `<REDACTED-R110296-synth-literal>` in 3 docs with
  a `<REDACTED-R110296-synth-literal>` placeholder marker
- Used `sed` to also redact sub-parts (`<REDACTED-subpart>`,
  `<REDACTED-subpart>`) — these
  sub-parts also matched `_is_common_value` since the
  detector searches for `L` (literal) extracted from
  `assert "L" in ...` patterns
- The full literal value is now in EXACTLY 1 source location:
  `mas-engineer/tests/test_r110279_runtime_var_skip.py`
  Z.125 (`L1 = "R110296S" + "<REDACTED-subpart>"`)
- Note: the literal is split across 2 string concatenations
  in the test source, so even the test source itself does not
  contain the full literal as a single string token. The
  detector's string-extractor concatenates the parts at
  scan-time.

## Lessons-learned (R110-78 category 3 rule: stale-static-source references)

When the SD-test detector searches for inline literals in
source files as potential stale-static-source drift
findings, those literals must appear in EXACTLY 1 source
location at scan-time. Documentation files (CHANGELOG,
STATUS, EVIDENCE) MUST NOT contain those literals in
narrative sections, code-block examples, or shell-command
examples. Use a placeholder marker
(`<REDACTED-R110296-synth-literal>`) instead. The full
literal value should be documented ONLY in the test
source file (where it's split across string
concatenation to avoid even single-string detector
matches in the test file itself).

This rule is now codified in the R110-78 skill and will
be applied to all future R110-285+ series commits.
