## Why this is documented, not fixed

Per **R110-24** and **R110-174**, amending published commits to
rewrite author headers is **verboten**. Force-push of rewritten
history is **verboten** per **R110-281** (force-push-verbot,
reflog: 15d04c9@{9}, eb6c9e1@{7}). The only safe options are:

1. Document the discrepancy (this commit). Future contributors can
   decide whether to (a) tolerate the author mix, or (b) introduce a
   future `git filter-repo` + force-push window for cleanup — which
   would itself require a R-code amendment of the policy.
2. Configure local git env (already done in this worktree:
   `git config user.name` = `Hermes-MAS-Engineer`,
   `git config user.email` = `Hermes@mas-engineer.local`). Future
   commits from this worktree will use the canonical identity.
   Note: `GIT_AUTHOR_*` environment variables override
   `git config` per `git-commit(1)`, so any wrapper script that
   sets those will still produce non-canonical authors — see
   "Future-proofing" below.

## Future-proofing (R-code for next sprint)

The root cause is likely a wrapper / hook / environment variable
that overrides `GIT_AUTHOR_NAME` / `GIT_AUTHOR_EMAIL`. Suggested
followup:

- Audit `.githooks/`, `scripts/`, and any IDE auto-commit plugin
  for `GIT_AUTHOR_*` exports.
- Consider a pre-commit hook that asserts
  `git var GIT_AUTHOR_IDENT` matches `Hermes-MAS-Engineer
  <Hermes@mas-engineer.local>` and warns (does not block) on
  mismatch. A non-blocking warn is consistent with the R110-281
  "immutable history" pattern.
